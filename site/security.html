Security

Security, in plain words.

Abnahme reads invoices, holds a converter's fee in escrow and signs on-chain transactions. This page says what we protect, how, which risks we accept for the hackathon demo, and what is still open.

Threat model in plain words

What we protect: the buyer's escrowed fee, the seller's right to be paid for good work, the correctness of the invoice that reaches the client, and the keys that sign on chain. On the left, what could go wrong. On the right, what stops it.

Threat

The converter delivers a broken or doctored invoice

What stops it

The pinned KoSIT validator and scenario, plus eleven content checks against the client's profile. The XML reader reads facts by exact path, so comments, CDATA or extensions cannot hide anything. The delivered bytes must match the result hash on chain.

Threat

The converter swaps the test after the money is locked

What stops it

The profile hash sits in the escrow's input_hash, and the validator keeps it fixed through every state change.

Threat

The converter takes the money despite a refusal

What stops it

In Disputed the on-chain validator allows no withdrawal by the seller. Only the buyer's AuthorizeWithdrawal releases it early.

Threat

The buyer agent crashes, or a dependency is down

What stops it

The buyer engine fails closed. If no inspection has passed 15 minutes before the deadline, it files a protective refusal and keeps inspecting while the money waits. It releases only the result hash it inspected.

Threat

The buyer refuses in bad faith

What stops it

Validator warnings count as minor and cannot justify a refusal. After the dispute window, Masumi's admins arbitrate on chain.

Threat

The seller leaves the buyer's money frozen

What stops it

The converter authorizes the refund itself 10 minutes before the dispute window closes, when a cure is not confirmed within 20 minutes, or when a cure fails to submit.

Threat

A stranger pushes the converter into a refund

What stops it

Disputes and the delivered result require the job's own token. Without it the converter answers 401.

Threat

Crafted invoice text tries to steer the task

What stops it

Recipient and amount must sit directly under the first line and cannot be set or hidden from inside the invoice text. The expected total always comes from the buyer. Text over 16,000 characters is refused, and whatever is read out is still checked against the pinned profile.

Threat

An inspection payment is replayed or misused

What stops it

A resent payment with the same body gets the stored report, with no second settlement; a different body gets 409. Reports are bound to the inspected document's hash, and a verdict counts only with a settled receipt.

Threat

Secrets leak from one process to another

What stops it

Each process gets its own env file with only its own secrets, and a guard refuses to start a process that holds another one's secret. The buyer never holds the admin key.

Threat

Tampered dependencies or images

What stops it

Container images are pinned by digest, the validator and its configuration by sha256, npm packages by lockfile, and CI actions by commit SHA. CI fails on an unpinned image.

Threat

Exposure on the local network

What stops it

Every service binds 127.0.0.1. New validator and mail containers run as non-root with a read-only filesystem and no capabilities.

What is pinned

  • KoSIT validator 1.6.3 and the XRechnung configuration 2026-08-31, by sha256, checked on every start.
  • The validator's Java image, the mail server, the Masumi Payment Service and its database, by image digest.
  • The payment service's setup build, by full commit hash.
  • npm dependencies by lockfile, installed with npm ci; Node.js 24.2 or newer, enforced.
  • GitHub Actions by full commit SHA.

Upstream

While building the refusal path we found that Masumi Payment Service 0.28.0 to 0.30.0 never refunds a V2 purchase automatically after the seller authorizes the refund. No funds are at risk, because only the buyer can spend that escrow, but it waits for an operator. We filed issue #1327 with on-chain evidence and a fix with a regression test in PR #1328 (open, awaiting review).
