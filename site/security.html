Security

Security, in plain words.

Abnahme reads invoices, holds a converter's fee in escrow and signs Cardano transactions. This page says what could go wrong, what stops it, and which risks we accept for the hackathon demo.

High findings

The four high findings.

None was in the escrow contract. All four were in our own code or documentation.

  • EINVOICE-1

    XML comments could fool the acceptance test

    The content checks could read a different IBAN, total or buyer VAT ID than the one the validator and the client's ERP read.

    Fixed in 0cff46a: a strict, namespace-aware XML reader reads each fact by exact path.

  • ESCROW-1

    The buyer engine failed open

    If it stopped before the refusal, the seller was paid at the deadline without an inspection.

    Fixed in ca81443: a protective refusal goes out by unlock − 15 min, and inspection continues from Disputed.

  • QA-2

    A restart abandoned paid work

    A restart left in-flight tasks open forever.

    Fixed in ab937bd and later rounds: graceful shutdown, and journals resume on the next start.

  • CLAIMS-1

    The README contradicted the chain

    It understated what was built and listed confirmed transactions as pending.

    Fixed in 140aec4: README rewritten and re-checked against the chain.

Threats

What could go wrong, and what stops it.

We protect the buyer's escrowed fee, the seller's right to be paid for good work, the correctness of the invoice that reaches the client, and the keys that sign on chain.

  • Threat

    The converter delivers a broken or doctored invoice

    What stops it

    The pinned KoSIT validator and scenario, plus content checks against the client's profile. The XML reader reads facts by exact path, so comments, CDATA or extensions cannot hide anything. The delivered bytes must match the result hash on chain.

  • Threat

    The converter swaps the test after the money is locked

    What stops it

    The profile hash sits in the escrow's input_hash, and the validator keeps it fixed through every state change.

  • Threat

    The converter takes the money despite a refusal

    What stops it

    In Disputed the on-chain validator allows no withdrawal by the seller. Only the buyer's AuthorizeWithdrawal releases it early.

  • Threat

    The buyer agent crashes, or a dependency is down

    What stops it

    The buyer engine fails closed. If no inspection has passed 15 minutes before the deadline, it files a protective refusal and keeps inspecting while the money waits.

  • Threat

    The buyer refuses in bad faith

    What stops it

    Validator warnings count as minor and cannot justify a refusal. After the dispute window, Masumi's admins arbitrate on chain.

  • Threat

    The seller leaves the buyer's money frozen

    What stops it

    The converter authorizes the refund itself 10 minutes before the dispute window closes, when a cure is not confirmed within 20 minutes, or when a cure fails to submit.

  • Threat

    Crafted invoice text tries to steer the task

    What stops it

    Recipient and amount must sit directly under the first line and cannot be set or hidden from inside the invoice text. The expected total always comes from the buyer. Text over 16,000 characters is refused.

  • Threat

    An inspection payment is replayed

    What stops it

    A resent payment with the same body gets the stored report, with no second settlement; a different body gets 409. A verdict counts only with a settled receipt.

  • Threat

    Secrets leak, or dependencies are tampered with

    What stops it

    Each process gets its own env file with only its own secrets. Images are pinned by digest, the validator by sha256, npm packages by lockfile and CI actions by commit SHA. Every service binds 127.0.0.1.

Accepted risks

Risks we accept for the demo.

All of them run on preprod only, with test funds. Each one is written down in SECURITY.md with its fix.

  • Masumi Payment Service 0.29.0 runs on end-of-life Node 20

    Preprod funds only, API on 127.0.0.1, wallet-scoped keys, image pinned by digest. No exploit was demonstrated.

    Fix: move to 0.30.0 on Node 24.

  • The running validator container has an older Java runtime

    It holds no secrets, and its rules mount is read-only. No exploit was demonstrated.

    Fix: recreate it with the pinned, hardened image.

  • The Sokosumi CLI is a global install outside every lockfile

    The exact version is installed, and today's tree matches a fresh resolution with 0 advisories.

    Fix: pin it in package.json.

  • @x402/* 2.26.0 was published without provenance

    It pulls a flagged zod; the advisory is not reachable from untrusted input (checked by reading the code, not by fuzzing).

    Fix: pin 2.29.0, published by CI with provenance.

Upstream

Two bugs in Masumi Payment Service 0.29.0 left refunds (issue #1327) and seller payouts after a batched cure (issue #1331) waiting for an operator. We sent fixes with regression tests in PR #1328 and PR #1332; until they are merged, our own repair loop completes both.
